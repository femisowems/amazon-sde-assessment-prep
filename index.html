Amazon SDE Online Assessment — should you take it tomorrow?

Everything below is drawn from a full research pass on the current 2025–2026 HackerRank format: what each section actually is, what decides the outcome, and a clear go / wait call for tomorrow. Labels show how solid each claim is — Official (Amazon / HackerRank), Reported (2026 candidate reports — useful, but anecdotal), Conflict (sources disagree; the invite wins).

Role: SDE II Format: HackerRank Deadline: within the 1-week window Sitting: ~2.5 hrs, one go, no pausing

The bottom line

Default call: WAIT — unless you clear all five checks tonight. You have a structural edge in the repo question if you pick Node.js. The risk is Q1: in this new format the single traditional problem is reported as LeetCode Medium to Medium-Hard in ~40 minutes — harder than old guides imply. There is no reported bonus for submitting on day 1 vs day 5, and 3–4 focused days is the highest-value move if tonight's checks fail. Use the readiness checker in §6 before you decide.

Mechanics that matter Official

  • Finish Coding (Q1) first — you cannot return to it after switching to the Code Repository section.
  • Q1 tests: 2 sample + 13 hidden (hidden ones show a lock icon). Validation is exact string matching. Most questions expect a returned value; console.log goes to Debug Output and doesn't score — but if a question expects printed output, remove debug prints before submitting or it can fail.
  • Q2: the IDE autosaves; if time runs out you're logged out and the most recent auto-saved version is evaluated. Run Tests runs a predefined set per task with pass/fail, errors and assertions shown. Do not modify README.md / read-only files, and do not change IDs/classes of existing UI elements — tests depend on them.
  • Setup: latest Chrome/Edge per your invite, disable browser extensions, enable third-party cookies, stable network (HackerRank calls ~10 Mbps “good”). Repo IDE initialisation can take up to a minute and is not counted in test time.

2 · Q1 — Traditional coding (the risk)

One problem, ~40 minutes, LeetCode Medium to Medium-Hard in the new format. A weak Q1 is not rescued by a strong Q2. Reported

Difficulty — then vs now

  • Old format (2 problems, 70–90 min): typically LeetCode Medium; first sometimes Easy-Medium, second Medium-Hard.
  • New format (yours): “It got harder, not easier… the old advice about Amazon OAs being easy is out of date.” A first-hand SDE II candidate rated his problem Medium-Hard and ran out of time despite being close.
  • Hard / exotic is rare in the OA itself. Don't spend tonight on Hard DP, segment trees, or trie exotica at the expense of Medium fluency.

Sources: Nyrion (31 candidate threads to 31 Oct 2026) · TakeUForward, first-hand SDE II · IGotAnOffer (updated 2 Oct 2026)

Scoring — what counts

  • Hidden tests dominate. HackerRank scores by test cases passed, including hidden ones — so partial credit is real, and a brute force passing some cases beats nothing.
  • Samples prove almost nothing (2 only). Always self-test: empty/minimum input, single element, duplicates, already-sorted / reverse, max-size shape, negative/zero if allowed.
  • Efficiency matters twice: slow code fails hidden cases on time limits, and Amazon states optimised solutions earn more than brute force. Official
  • No complexity essay needed. There's no interviewer and no reported free-text complexity question — scoring is test-case based. Clean names and a one-line comment on a non-obvious invariant are cheap insurance; don't burn timed minutes on more.
  • No published pass mark. Any “% needed to pass” figure on a prep site is anecdotal / unverified — see §8.

Patterns that keep appearing (2025–2026 reports, convergent)

Problems are usually wrapped in a logistics story — warehouse / delivery / grid placement, merging shipments, server rates, inventory, returns — but underneath it's a standard pattern. The skill is stripping the story: rewrite inputs/outputs plainly, note constraints, name the pattern before coding. Long statements + large constraints signal the intended solution is O(n log n) or O(n), not O(n²).

  1. Arrays / strings + hash map/set counting — frequency maps, grouping, dedup, subarray/substring conditions.
  2. Sliding window + two pointers — longest/shortest substring or subarray under a constraint; container/pair problems.
  3. Prefix sums + binary search — including binary-search-on-answer / partitioning an array to minimise the largest part.
  4. Greedy + sorting / intervals — merge/sweep intervals, scheduling, lexicographically-best construction; monotonic stack in some reports.
  5. Graphs / grids: BFS, DFS, multi-source BFS — shortest steps, spread/rotting-style propagation, connected components.
  6. Heaps / priority queues — top-K, merging, streaming extremes.
  7. Modest DP — 1-D partition / string DP, knapsack-like or job-scheduling DP.
  8. Simulation / rates — process events in order exactly as specified; careful reading beats cleverness.

Sources: Calibrd (checked Oct 2026) · PraxisAI (updated 5 Nov 2026). Note: topic-frequency percentages on some blogs (e.g. “arrays 76%”) are unverifiable scraping estimates — the research did not treat them as data.

Your 40-minute Q1 workflow

0–5 Read, restate, note constraints, brute force in your head  ·  5–10 Pick the pattern, sanity-check on the sample by hand  ·  10–30 Code the optimal-or-better version  ·  30–35 Run samples + your own edge cases, fix  ·  35–40 Optimise the obvious bottleneck — or lock in the best partial-credit version, Save & Proceed, and don't look back.

JavaScript traps to fix tonight

  • Array.sort() is lexicographic without a comparator — always (a, b) => a - b for numbers.
  • No built-in heap or deque in JS. Write a minimal MinHeap class once tonight; for BFS use a queue with an index pointer — don't shift()/slice a queue on large inputs.
  • Know Map/Set iteration cold; remember string immutability costs on repeated concatenation.

The Q1 prompt kit — for tonight's practice, not the test

Q1 has no AI assistant — outside AI in Q1 is prohibited and monitored (see §7), so there are no prompts to use during Q1. What a prompt kit can do for Q1 is make tonight's drills sharper: use the first six with any chat AI before the sitting to generate problems, ration hints, and review your attempts without being handed solutions. The last three aren't AI prompts at all — they're the questions to ask yourself, in order, inside the test. Rehearse them tonight until they're automatic.

Tonight · Generate a drill problem
“Give me one LeetCode Medium problem that uses [pattern, e.g. sliding window]. Problem statement and constraints only — no hints, no approach, no code. I'll solve it timed in JavaScript.”
Keeps the rep honest: you practise pattern recognition and coding under the clock, not reading a walkthrough. Rotate the pattern across the §6 practice list.
Tonight · Hint ladder, when stuck in practice
“I'm stuck on this problem after 15 minutes: [paste the statement]. Give me exactly one hint — the pattern name and the key observation — no code and no full solution.”
One rung at a time. If the first hint doesn't unblock you in 5 minutes, ask for one more rung — never jump straight to the editorial, or the rep teaches you nothing.
Tonight · Review a finished attempt
“Here is the problem and my JavaScript solution: [paste both]. Don't rewrite it. Tell me: (1) is it correct — name a specific input that breaks it, if one exists; (2) its time and space complexity; (3) the single biggest inefficiency.”
The post-rep review that matters: a breaking input teaches more than a model solution. Fix the flaw yourself first, then compare approaches if you want.
Tonight · Build your edge-case list
“For this problem — [paste the statement] — list the edge cases I should test before submitting: minimum or empty input, single element, duplicates, already sorted, reverse sorted, maximum-size input, and any boundary values the constraints allow.”
Hidden tests are where Q1 is won or lost, and they're mostly edge cases. Run this once per practice type tonight and you'll start generating the list unaided.
Tonight · Learn a pattern cold
“Teach me the [pattern, e.g. binary search on the answer] template for JavaScript: when it applies, the invariant it maintains, and a minimal skeleton I can type from memory. Then give me one small example to trace by hand.”
Directly feeds the readiness checker's “templates from memory” box. Close the chat afterwards and re-type the skeleton from memory — that's the actual test of whether it stuck.
Tonight · Sharpen the complexity reflex
“For this problem — [paste the statement] — state the brute-force complexity and the best achievable complexity, numbers only (e.g. ‘brute force O(n²), optimal O(n log n)’). Don't describe the optimal algorithm.”
Trains the move you'll make at minute 2 of the real Q1: read the constraints, derive the target complexity, and let that pick the pattern — without spoiling the problem during drills.
In the test · Minutes 0–5, ask yourself
“What are the inputs and the exact output? What do the constraints rule out? Which pattern is this — hash map, sliding window, prefix sums, binary search, greedy/intervals, BFS/DFS, heap, or modest DP? What does the brute force look like, and where exactly does it waste work?”
Your recognition checklist — no AI involved, just the four questions that turn a wall of story text into a named pattern before you write a line. Say them in this order, every time.
In the test · Stuck around minute 20, ask yourself
“What simpler version passes most tests? Lock in the brute force — or the sort-based O(n log n) version — run the samples now, and only optimise with whatever time is left.”
Partial credit is real and hidden tests dominate, but zero passing code scores zero. A working suboptimal solution on the board beats an optimal one that exists only in your head at minute 40.
In the test · Final 5 minutes, ask yourself
“Have I tested minimum/empty input, a single element, duplicates, and a maximum-size shape? Am I returning the value (not console.log)? Are there debug prints to remove? Is the numeric sort using (a, b) => a - b?”
The pre-submit sweep, built from the scoring notes and JS traps above. Two minutes here routinely saves more test cases than two more minutes of optimising.
Boundary, stated plainly: prompts 1–6 are for preparation only — tonight, in a separate tool, on practice problems. In the real sitting, Q1 is unaided: no chat AI, no second device, no outside resources (§7). Prompts 7–9 are deliberately self-prompts — questions you run in your own head — because that's the only “assistant” Q1 allows. The AI assistant exists only in Q2, which is what the §3 kit is for.

Full-solve prompts — get a complete, worked solution

When you want the whole question solved end-to-end — not a hint — use these two on practice problems tonight, in a separate AI tool outside the assessment. The workflow that makes them useful: attempt the problem timed and unaided first, then run the matching prompt, compare its solution to yours line by line, and re-type the corrected version from memory. That turns a full solution into pattern fluency instead of just an answer you read once.

Practice only · Q1 — full solve
“Solve this problem completely in JavaScript (Node.js): [paste the full problem statement, constraints, function signature, and sample input/output]. Do not give hints or a partial approach — give the finished solution. Provide: (1) a 2–3 sentence restatement of what is being asked, stripped of the story; (2) the pattern you are using and why the constraints require it; (3) complete, runnable code with no placeholders or TODOs — return the value (do not rely on console.log for the answer), use (a, b) => a - b for numeric sorting, and handle empty/minimum input, a single element, duplicates, and maximum-size input; (4) time and space complexity; (5) a step-by-step walkthrough on the sample; and (6) at least 6 test cases — the samples plus edge cases — with the expected output for each and a check that your code produces it. If the brute force differs from the optimal solution, show the optimal one only.”
One paste, one complete answer: code you can run as-is, the reasoning behind it, and a test set that proves it — including the edge cases hidden tests usually target. Replace the bracketed part with the whole practice problem, signature included, or the code may not match the expected function shape.
Practice only · Q2 repo task — full solve
“Solve this practice repo task completely. README / ticket: [paste it]. Failing tests and exact error output: [paste them]. Relevant files: [paste each file, labelled with its file name]. Give the finished fix, not hints: (1) for every bug, name the file and function, state the root cause in one line, and show the exact corrected code for that function or block — complete enough that I can apply it verbatim, with no placeholders; (2) if a whole file needs replacing, give the complete corrected file; (3) do not change the README, the tests, or any existing element IDs/classes; (4) check the fix against every rule in the README — required-field validation returning 400 (not 500), 404 for missing records, 401/403 where permission applies, changes actually saved/persisted, and the correct status code and response field names; and (5) finish with a checklist mapping each failing test to the change that makes it pass, plus any remaining edge case — duplicates, empty or missing fields, wrong user — that could still fail. ”
Built for a practice repo drill: paste the ticket, the failing output, and the handler files, and you get an apply-ready fix per file plus a test-by-test checklist to verify against when you Run Tests. It only works if you paste the actual files — without them, any AI can only guess at the codebase.
Use these outside the sitting only. In the live assessment they won't do what they do in practice: Q1 permits no outside AI at all (§7), and Q2's built-in assistant is documented to give guidance “without providing the full solution” — it will decline a request like prompt 2, and the transcript is visible to your evaluator (§3). In the real Q2, fall back to the §3 kit: locate, trace, and narrow one bug at a time, and write every fix yourself.

3 · Q2 — Repo + AI assistant (your edge, if you pick Node)

A throughput test, not an algorithms test. Candidates who lose do so by reading the whole codebase, picking an unfamiliar stack, or running out of clock — not because a bug was deep. Reported

What it actually is

  • Small multi-file web app in a full browser VS Code IDE. The README is the contract. HackerRank's own examples: a React app or Express server; tasks like “fix a bug on the Customer dashboard” or “add a feature to check whether Express delivery is available.” Official
  • A short ticket names 2–4 broken behaviours; the suite has ~6 tests (reports range 3–8). Sometimes there's one bug not in the ticket, found only by reading failing tests.
  • Mostly bug-fixing; some tasks are feature-building / finishing a missing piece. Domains rotate (watchlist, issue tracker, wallet, loans, car rental, blog, returns) — irrelevant; the handler shape is constant.

Sources: HackerRank · Nyrion · Bugnik (22 Oct 2026)

The bugs are shallow handler bugs

  • Missing validation → 500 instead of 400
  • Missing existence check → no 404
  • Mutate-but-never-save (missing save/update call)
  • Wrong route/path or method registration
  • Wrong status code or response shape / field name
  • Duplicate check comparing the wrong type or field
  • Search filter missing, case-sensitive search, wrong sort direction
  • Frontend showing the wrong user's / wrong filtered data because the API/query is wrong — fix the API layer first
Pick Node.js. Reported stack options include Node.js (MERN / Express + MongoDB), Java + Spring Boot, Python + Django, and C++ in at least some reports (Flask in one synthesis) — lists vary by role/cycle, so the list in your invite/demo is the only authoritative one. Official on the lock: you select the framework before starting and cannot switch once the test starts. Candidates who picked Spring Boot without daily Spring fluency report losing most of the hour to framework friction and finishing 2/6. Pick the stack you can read and debug blind. Sources: HackerRank · Bugnik · Nyrion

The AI assistant — a librarian, not a fixer

What it does Official

  • Built into the repo IDE. Gives “contextual and coding guidance, without providing the full solution.”
  • Can explain the codebase, point to where a change belongs, help debug errors you paste in, and suggest syntax/templates you can Apply at the cursor.
  • Optional; you won't be penalised for using it, and interactions are not considered in your score — but the conversation is recorded and the transcript is visible to your evaluator. Write prompts as if a hiring manager will read them, because one may.
  • Repo-only. GenAI is not permitted in Q1.

What candidates report Reported

  • It will say which file handles a route, explain a block, say what a test checks. Ask it to fix the bug or edit the file and it usually declines; narrow questions about one specific error occasionally yielded a hint.
  • Some found it slow, misleading, or limited to the open file. Verify everything it says by running tests.
  • Don't confuse it with HackerRank's newer interview product where an agent can edit files — that's a different configuration. Plan to write every fix yourself.

Sources: Nyrion · TakeUForward

Prompting rules: ask where / what / why-this-error, never “fix it” · paste the exact error + failing test name · one file/function at a time · never wait on it — keep tracing while it answers · never Apply a suggestion you don't understand.

The Q2 prompt kit — copy-ready, in the order you'll use them

Twelve prompts covering the whole hour. Replace the [bracketed] parts with your actual file, route, or test name — specificity is what makes the assistant useful; vague prompts get vague answers. Each one is deliberately framed as where / what / why, because that's what the assistant answers well, and because a transcript full of “explain this / locate that” reads like a senior engineer working — which matters, since the evaluator can see it. Tap Copy to grab a prompt for your practice drill tonight; in the real test, type or paste them into the AI panel.

Minute 0–5 · Orientation
“Give me a quick map of this codebase: which files handle routing, request handling, data storage, and validation? Keep it to file names and one line each.”
Your first move alongside reading the README. Gets you the lay of the land in one answer instead of opening every file.
Minute 0–5 · Orientation
“According to the README, what are the exact expected behaviours for [feature, e.g. creating an item] — required fields, status codes, and error cases?”
The README is the contract. This pins the expected behaviour before you look at any code, so you can spot where the code disagrees with it.
After first Run Tests · Triage
“These tests are failing: [paste the failing test names]. For each one, which route and which file/function is it most likely exercising?”
Turns a wall of red tests into a worklist with locations. This is the single highest-value prompt in the kit — it converts test output into a map.
Per failing test · Understand the test
“What exactly does the test ‘[test name]’ check? Walk me through the request it sends and the response it expects, step by step.”
Never fix against a test you haven't understood. The expected status code and response shape in the test tell you what “correct” is.
Per bug · Locate it
“Trace the request flow for [method + route, e.g. POST /items]: which files and functions does it pass through, in order, from the route definition to the data layer?”
Gives you the exact chain to walk — route → handler → service → model — instead of hunting through folders under time pressure.
Per bug · Narrow the cause
“The test expects a [expected status, e.g. 400] when [condition, e.g. the name field is missing], but the API returns [actual status, e.g. 500]. Where in the handler for [route] should that validation happen, and what check is missing?”
The workhorse prompt. Expected-vs-actual plus the route is exactly the framing that gets a precise, usable answer — and it matches the shallow-bug pattern (missing validation, missing 404, forgotten save).
When you hit an error · Debug
“I'm getting this error: [paste the exact error message and stack trace]. Which line in [file] is causing it, and why?”
Always paste the real error — never paraphrase it. The assistant is good at reading stack traces; it's poor at guessing from a summary.
Reading unfamiliar code · Explain
“Explain what [function name] in [file] does, line by line. In particular: does it save/persist the change it makes, and what does it return?”
The mutate-but-never-save bug hides inside functions that look fine at a glance. Asking explicitly about persistence and return value surfaces it fast.
Syntax / framework gaps · Unblock
“What's the correct Express syntax for [the thing you're doing, e.g. reading a route parameter / sending a 404 JSON response]? Just the pattern, briefly.”
Legitimate use of the assistant: it will supply syntax and templates. Asking for the pattern — not the fix — keeps you moving without burning minutes on docs you can't open.
After each fix · Verify
“I changed [file] so that [one-line description of your fix]. Which other behaviours or tests could that change affect?”
A cheap regression check before you re-run. Then Run Tests anyway — the assistant's opinion never substitutes for a green suite.
Minute 45+ · Hunt the unlisted bug
“All the ticket's tests pass now. Based on the README rules, which edge cases are most likely to still be broken — empty or missing fields, duplicates, wrong user, wrong status codes?”
For the final sweep. Reports say there's sometimes one bug not named in the ticket; this prompts a checklist to test against the README yourself.
Stuck past ~10 min on one bug · Reframe
“I'm stuck on ‘[test name]’. The test sends [request] and expects [expected], but gets [actual]. What are the three most likely causes, in order, and how would I check each one?”
Your escape hatch. A ranked list of hypotheses with checks beats one confident guess — work down the list, testing each, instead of deep-diving the first idea.
What not to ask: “Fix this bug,” “Write the code for…,” or pasting a whole file and asking what's wrong with it. Candidates report the assistant usually declines to write fixes — so you lose clock time and the transcript shows you asking for the solution instead of the reasoning. If it declines or gives you something vague, don't argue with it: narrow the question to one file, one error, one expected-vs-actual pair (prompt 6), and keep tracing the code yourself while it answers. Every fix is yours to write; the assistant is for orientation, location, and explanation only.

The 60-minute Q2 workflow

  1. 0–5  Read the README fully. Run Tests before touching code. Failing test names are your map.
  2. 5–10  If it doesn't build/install, fix that first. Ask the assistant only for orientation: “Which file/route handles X?”
  3. 10–45  One failing test at a time: read the test → trace route → handler → service → model/helper → find the line that disagrees with the README → smallest possible fix → Run all tests.
  4. 45–55  Green? Re-read the README rules; check boundaries, empty/missing fields, duplicates, wrong-user, error codes. Hunt the unlisted bug.
  5. 55–60  Final full Run Tests. Confirm the last change saved. Submit.

Pace check: ~10 minutes per bug/test. At minute 30 with 0–1 tests green, stop deep-diving and triage the cheapest-looking failures first. Partial credit is real here — reports include candidates advancing at 4–5 of 6. Reported

Handler shape to rehearse (Node/Express)

Route → validate → lookup / 404 → auth / permission → mutate → save → status / shape. Status codes to know cold: 200 · 201 · 400 · 401 · 403 · 404 · 500.

5 · Work Style Surveys (~10 min on the label — two surveys)

Profile fit, not knowledge. The real risk isn't a “wrong” answer — it's an inconsistent one.

What they are Reported

  • Forced-choice / rating items built around the 16 Leadership Principles. Typical format: two statements side by side — pick which is more like you, on a “Most like me / More like me” scale with no neutral middle; some versions use Likert ratings.
  • Example of the kind of pair (from prep guides, not a leaked item): “I like things clearly structured” vs “I look forward to learning new things.”
  • Your “two surveys” matches July 2026 reports of ~15 single-answer items + ~35 forced-choice pairs — which took that candidate 25–30 minutes despite a ~10-minute quote. Budget more time than the label.
  • Amazon's own line (via summaries): Workstyles needs no practice — answer as the authentic you, don't overthink.

Sources: IGotAnOffer · Inbyte prep guide (updated 1 Nov 2026, as cited in the research report).

Honest, but strategic

  • Are there “right” answers? Not per item — pairs often pit two desirable traits against each other. But there is a coherent vs incoherent profile: scoring reportedly compares your pattern to LP-aligned profiles. Claims of a secret answer key are prep-site marketing — unverified.
  • Consistency traps: the same trait returns reworded, paired against different alternatives. Endorsing both “I decide fast on available data” and later “I always wait for complete data” as most like you — or maxing the flattering extreme on everything — produces detectable contradictions. (The exact penalty is unknown; Amazon doesn't publish the algorithm.)
  • Approach: read the 16 LPs once tonight so the vocabulary isn't new → answer as yourself at work on a good day → first instinct, a few seconds per item → when two good traits collide, pick the one that's truly more characteristic of you → keep a steady pace, don't reverse your philosophy halfway through.

7 · Rules, proctoring & logistics

Your invite controls. Assume the strictest reading — proctoring is configured per requisition, and Amazon doesn't publish which add-ons are on for yours.

What's tracked

  • Amazon (official, via summaries): browser usage is logged during coding; using Print Screen may terminate your session / lock you out; avoid copy-pasting; parts of the OA need a webcam (takes your picture); candidates in North America need a student/government photo ID.
  • HackerRank default (every test): copy-paste tracking, tab/focus tracking (frequency + duration away), and MOSS code-similarity comparison with other submissions.
  • Optional employer add-ons: AI plagiarism detection, periodic webcam image proctoring, Secure Mode (full-screen, single monitor, blocks external paste), Proctor Mode (screen recording + AI review), Desktop App mode. Which ones Amazon enabled for your test is not published.
  • Webcam reports conflict: Oct 2026 reports describe webcam + face snapshot + ID photo before start; Apr–Aug reports describe no camera / no browser lock, only a paste warning. Assume webcam + screen + ID are on. Conflict
  • The Q2 AI assistant transcript is recorded and visible to your evaluator (not scored). Official

What counts as a violation

  • Any outside AI / person / website / device in Q1, or outside the built-in assistant in Q2
  • Another person helping; copying code (MOSS + paste logs)

  • Impersonation / ID mismatch

  • Lose internet? Submitted work is saved, the timer keeps running while offline, and the test ends at the scheduled time even if disconnected. You can log back in and continue if time remains.
  • Logging out ends your attempt immediately — never log out.
  • In-test issues: use ? → Report a problem. HackerRank cannot extend time, reschedule, or share results — the recruiter decides on extension or re-invite.
  • Practical: wired connection if possible, charger plugged in, notifications off, nothing else running, phone away (not as a second screen). Results, cooldown, reuse

  • No published passing score; HackerRank does not send scores to candidates — Amazon owns the report and decides what to share.
  • Timing: SDE II official line (via summaries) is notification within 2 days of completing. Candidate reality ranges from next day to ~2 weeks; a first-hand SDE II rejection arrived at 2 days. Check spam. For multi-part OAs, contact Amazon if no completion email arrives within 24 hours of a part — and complete the final feedback survey; skipping it reportedly delays results.
  • Cooldown if you fail (SDE II): encouraged to reapply in 6 months. Official There is no self-serve retake — only a recruiter re-invite. (For new-grad OAs no retake rule is published and reports conflict.)
  • Reuse (SDE II): one OA result counts for several SDE II roles — you shouldn't need to re-sit for every SDE II application. Hiring decisions still stay per-requisition.
  • Deadline: typically 7 days from send (typically within the 1-week window). Missed deadlines generally cannot be extended — using the full week is normal and expected; don't let the link expire silently.
